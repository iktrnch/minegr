# start-command

## Summary

`minegr start` starts a configured Minecraft server through its per-server daemon and waits until the server is ready.

## Behaviour
Prints `Starting server…`, starts the daemon, and waits quietly for the server's `Done!` message. On success, prints `Server started successfully.`

Startup times out after five minutes. Failure output goes to stderr and includes the last 100 available lines and Minecraft's `logs/latest.log` path (using the same tail logic as [logs command](logs.md)).
## Workflow
1. Load and validate the configuration without installing missing dependencies
2. Use the configuration UUID to connect to `$XDG_RUNTIME_DIR/minegr/<uuid>.sock`
3. Remove an unresponsive stale socket, then launch the daemon through minegr's internal daemon mode
4. Wait for the daemon to report readiness, failure, or timeout
## Rules
- The configuration must contain a UUID generated by `minegr init`
- Only one daemon and Java process may run for a server
- A matching responsive socket reports:
```text
Server is already running, stop it with `minegr stop`
```
- If the socket's daemon has the same UUID but a different canonical configuration path, report that the UUID is already running at another path and suggest `minegr init --uuid`
- Failure, timeout, or Ctrl-C stops the Java process
- Missing managed files fail with an actionable instruction to rerun `minegr init`; Minegr never downloads or reconstructs them during `start`. A configured Fabric launcher may perform its own first-run bootstrap.
- The daemon removes its socket after initial startup failure, final stop, or unrecoverable daemon failure. An unexpected Java exit after readiness leaves the daemon and socket in `failed`; restart retains them throughout.
## Failure cases

- The configuration has no UUID.
- Java is unavailable or incompatible, or a managed file is missing or differs from the declarative configuration.
- Startup fails, is interrupted, or exceeds five minutes.
## Implementation
`minegr start` launches the current executable in an internal daemon mode and communicates with it through a Unix socket. Daemon lifecycle and protocol details belong in [daemon](../daemon.md)
